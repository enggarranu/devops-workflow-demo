One CI pipeline, two operating systems, and a rollback proven on every run.

Aplikasi web yang sama dideploy ke nginx di Linux dan ke IIS di Windows lewat satu workflow, sampai ke rollback yang dibuktikan ulang tiap run.

The same web app deployed to nginx on Linux and to IIS on Windows through one workflow, down to a rollback that is re-proven on every run.

Setiap run mendeploy dua rilis, merollback, lalu membuktikan rilis lama benar-benar kembali dilayani. Seluruhnya terjadi di dalam GitHub runner.

Every run deploys two releases, rolls back, then proves the old release is actually being served again. All of it happens inside GitHub runners.

01 TriggerTrigger

Satu workflow, dua job. Bukan matrix: hampir setiap step berbeda isinya antar sistem operasi, dan matrix hanya akan menyembunyikan perbedaan yang justru mau ditunjukkan.

One workflow, two jobs. Not a matrix: nearly every step differs between the two operating systems, and a matrix would only hide the very differences this demo exists to show.

.github/workflows/deploy.yml
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  linux:
    runs-on: ubuntu-latest
  windows:

02 PackagePackage

Perbedaan paling dangkal di seluruh pipeline: dua perkakas arsip yang melakukan hal yang sama. Keduanya menaruh isi folder di akar arsip, supaya hasil bongkarnya langsung berupa index.html di root rilis.

The shallowest difference in the whole pipeline: two archive tools doing the same thing. Both put the folder's contents at the archive root, so unpacking yields index.html directly at the release root.

Linux
tar -czf app.tar.gz -C app .
Windows
Compress-Archive `
  -Path app\* `
  -DestinationPath app.zip -Force
03 Siapkan web serverSet up the web server

Beda biaya yang nyata, walau tidak sebesar yang biasa diduga. nginx tidak ada di image dan harus dipasang. IIS sebagian sudah ada: di run terakhir, 4 dari 7 fitur sudah menyala dan hanya 3 yang perlu dinyalakan sebagai Windows optional feature. Tetap jadi langkah terlama di job Windows, tapi hitungannya detik, bukan menit.

A real difference in cost, though smaller than usually assumed. nginx is absent from the image and must be installed. IIS is partly there already: on the last run, 4 of its 7 features were enabled and only 3 had to be turned on as Windows optional features. Still the longest step in the Windows job, but measured in seconds, not minutes.

04 DeployDeploy

Pola yang sama di kedua sisi: rilis masuk ke folder sendiri yang tidak pernah disentuh lagi, lalu satu pointer diarahkan ke folder itu. Yang berbeda cuma bentuk pointer-nya. Konsekuensinya tidak pernah ada file yang sedang dilayani yang perlu ditimpa, jadi seluruh persoalan file lock Windows tidak muncul di jalur deploy.

The same pattern on both sides: each release goes into its own folder that is never touched again, then a single pointer is aimed at that folder. Only the shape of the pointer differs. The consequence is that no file being served ever needs to be overwritten, so the whole Windows file-locking problem never appears on the deploy path at all.

Linux — symlinkLinux — symlink
tar -xzf "$PACKAGE" -C "$RELEASE_DIR"

# cap build id, supaya tiap rilis bisa
# dibedakan dari luar lewat HTTP
find "$RELEASE_DIR" -type f -name '*.html' -print0 \
  | xargs -0 --no-run-if-empty \
      sed -i "s/__BUILD_ID__/${BUILD_ID}/g"

# catat tujuan rollback sebelum swap
readlink -f "$CURRENT" > "$PREVIOUS"

# ln -sfn langsung ke current tidak atomic:
# ada jeda tanpa symlink. mv -T membuat
# pergantiannya satu rename tunggal.
ln -sfn "$RELEASE_DIR" "$CURRENT.tmp"
mv -T "$CURRENT.tmp" "$CURRENT"
tar -xzf "$PACKAGE" -C "$RELEASE_DIR"

# stamp the build id, so each release can be
# told apart from the outside over HTTP
find "$RELEASE_DIR" -type f -name '*.html' -print0 \
  | xargs -0 --no-run-if-empty \
      sed -i "s/__BUILD_ID__/${BUILD_ID}/g"

# record the rollback target before swapping
readlink -f "$CURRENT" > "$PREVIOUS"

# ln -sfn straight onto current is not atomic:
# there is a gap with no symlink. mv -T makes
# the switch a single rename.
ln -sfn "$RELEASE_DIR" "$CURRENT.tmp"
mv -T "$CURRENT.tmp" "$CURRENT"

app_offline.htm sengaja tidak dipakai. File itu hanya dihormati handler ASP.NET dan ASP.NET Core Module, bukan static file handler IIS, jadi untuk site static HTML seperti ini tidak akan pernah tampil.

app_offline.htm is deliberately not used. It is honoured only by the ASP.NET and ASP.NET Core Module handlers, not by the IIS static file handler, so on a static-HTML site like this one it would never appear at all.

05 Smoke testSmoke test

Dua pengecekan, bukan satu. Build id baru harus ada, dan build id lama harus sudah tidak ada. Tanpa pengecekan kedua, test ini tetap lolos walaupun pointer rilisnya tidak pernah berpindah — dan itu berarti rollback bisa rusak tanpa ada yang tahu.

Two checks, not one. The new build id must be present, and the old one must be gone. Without the second check this test still passes even if the release pointer never moved — which means rollback could be broken and nobody would find out.

Linux
# -f membuat curl exit non-zero untuk 4xx/5xx,
# jadi HTTP error tidak lolos sebagai body kosong
body="$(curl -fsS --max-time 10 "$URL")"

# -F: cocokkan sebagai teks biasa. Build id
# mengandung titik, dan tanpa -F titik itu
# cocok dengan karakter apa pun.
grep -qF -- "$MUST_CONTAIN"     <<< "$body"
grep -qF -- "$MUST_NOT_CONTAIN" <<< "$body"
# -f makes curl exit non-zero on 4xx/5xx, so an
# HTTP error cannot slip through as an empty body
body="$(curl -fsS --max-time 10 "$URL")"

# -F: match as plain text. The build id contains
# a dot, and without -F that dot would match
# any character at all.
grep -qF -- "$MUST_CONTAIN"     <<< "$body"
grep -qF -- "$MUST_NOT_CONTAIN" <<< "$body"
Windows
# -UseBasicParsing: jangan bergantung pada
# mesin DOM Internet Explorer, yang tidak ada
# di image runner
$r = Invoke-WebRequest -Uri $Url `
  -UseBasicParsing -TimeoutSec 10

# .Contains(), bukan -match, supaya build id
# diperlakukan sebagai teks dan bukan regex
$r.Content.Contains($MustContain)
$r.Content.Contains($MustNotContain)
# -UseBasicParsing: do not depend on the
# Internet Explorer DOM engine, which is not
# present in the runner image
$r = Invoke-WebRequest -Uri $Url `
  -UseBasicParsing -TimeoutSec 10

# .Contains(), not -match, so the build id is
# treated as text rather than as a regex
$r.Content.Contains($MustContain)
$r.Content.Contains($MustNotContain)

Kedua sisi mencoba lima kali dengan jeda dua detik sebelum gagal keras. Bukan kosmetik: di Windows, app pool baru saja di-recycle dan worker process yang baru belum tentu langsung siap melayani. Tanpa retry, pipeline-nya flaky, dan flaky-nya muncul tepat saat demo.

Both sides retry five times with a two-second gap before failing hard. Not cosmetic: on Windows the app pool has just been recycled, and the fresh worker process is not necessarily ready to serve straight away. Without retries the pipeline is flaky, and the flakiness shows up exactly during a demo.

06 RollbackRollback

Rollback bukan jalur kode khusus, cuma deploy ke arah sebaliknya, memakai mekanisme yang identik. Artinya rollback tidak bisa busuk tanpa deploy ikut busuk juga. File previous dihapus setelah dipakai, jadi rollback kedua berturut-turut adalah no-op yang eksplisit, bukan toggle bolak-balik.

Rollback is not a special code path, just a deploy in the opposite direction using an identical mechanism. That means rollback cannot rot without deploy rotting too. The previous file is deleted once used, so a second rollback in a row is an explicit no-op rather than a toggle back and forth.

Linux — 1 operasiLinux — 1 operation
TARGET="$(cat "$PREVIOUS")"

ln -sfn "$TARGET" "$CURRENT.tmp"
mv -T "$CURRENT.tmp" "$CURRENT"

rm -f "$PREVIOUS"
Windows — 2 operasiWindows — 2 operations
$target = Get-Content -Path $previous |
          Select-Object -First 1

Set-ItemProperty "IIS:\Sites\demo" `
  -Name physicalPath -Value $target

# langkah yang tidak ada padanannya di Linux.
# mengganti pointer saja belum menjamin
# request berikutnya melihat isi baru.
Restart-WebAppPool -Name demo

Remove-Item -Path $previous -Force
$target = Get-Content -Path $previous |
          Select-Object -First 1

Set-ItemProperty "IIS:\Sites\demo" `
  -Name physicalPath -Value $target

# the step with no Linux counterpart.
# swapping the pointer alone does not
# guarantee the next request sees the change.
Restart-WebAppPool -Name demo

Remove-Item -Path $previous -Force
07 Lock probeLock probe

Stage ini tidak mendeploy apa pun. Tugasnya menguji klaim yang paling sering diucapkan tentang dua sistem operasi ini, dan memecahnya jadi dua bagian karena hanya satu bagiannya yang deterministik.

This stage deploys nothing. Its job is to test the claim most often repeated about these two operating systems, and to split it in two — because only one half of it is deterministic.

Linux — diizinkanLinux — allowed
# fd 9 memegang file ini
exec 9< "$held"

printf 'isi-baru\n' > "$held"  # berhasil
rm "$held"                     # berhasil

# nama hilang dari direktori, tapi inode-nya
# belum dibebaskan: pemegang fd tetap membaca
cat <&9
# fd 9 holds this file open
exec 9< "$held"

printf 'new\n' > "$held"   # succeeds
rm "$held"                 # succeeds

# the name is gone from the directory, but the
# inode is not freed: the fd holder still reads
cat <&9
Windows — ditolakWindows — blocked
# FileShare.None: selama handle ini terbuka,
# tidak ada proses lain yang boleh membuka
# file ini untuk apa pun
$stream = [System.IO.File]::Open($held,
  [System.IO.FileMode]::Open,
  [System.IO.FileAccess]::Read,
  [System.IO.FileShare]::None)

[System.IO.File]::WriteAllText(
  $held, 'isi-baru')      # IOException
[System.IO.File]::Delete(
  $held)                  # IOException
# FileShare.None: while this handle is open, no
# other process may open this file for anything
# at all
$stream = [System.IO.File]::Open($held,
  [System.IO.FileMode]::Open,
  [System.IO.FileAccess]::Read,
  [System.IO.FileShare]::None)

[System.IO.File]::WriteAllText(
  $held, 'new')           # IOException
[System.IO.File]::Delete(
  $held)                  # IOException

Eksperimen di atas diassert: kalau hasilnya tidak sesuai, job-nya merah. Eksperimen satunya tidak, dan hasilnya justru yang paling menarik: menimpa index.html yang sedang dilayani IIS berhasil, dan request berikutnya langsung menampilkan isi baru — persis seperti nginx. Untuk konten static, dua sistem operasi ini berperilaku sama. Lock-nya baru muncul di eksperimen B, yaitu di level primitif sistem operasi, bukan di jalur IIS.

The experiment above is asserted: if the result differs, the job goes red. The other one is not, and its result is the more interesting half: overwriting the index.html IIS is serving succeeds, and the very next request shows the new content — exactly like nginx. For static content the two operating systems behave the same. The lock only appears in experiment B, at the OS primitive level, not on the IIS path.

Dua halaman hasil itu ditulis ulang oleh pipeline tiap kali run selesai, jadi isinya selalu run yang terakhir: build id, commit, metode deploy, hasil smoke test, dan ke build mana rollback diuji. Keduanya dilayani GitHub Pages, bukan nginx atau IIS; runner yang mengerjakannya sudah dihancurkan begitu job selesai.

Those two result pages are rewritten by the pipeline every time a run finishes, so they always show the latest one: build id, commit, deploy method, smoke test results, and which build the rollback was tested against. Both are served by GitHub Pages, not by nginx or IIS; the runners that did the work were destroyed the moment their jobs finished.
